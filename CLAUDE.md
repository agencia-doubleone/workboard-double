## Comandos

- `npm run dev`: servidor de desenvolvimento. O preview do Claude (`.claude/launch.json`) sobe na porta **3001**. O login só funciona na origem igual a `BETTER_AUTH_URL`, então o `.env.local` precisa apontar para a porta que estiver em uso.
- `npm run lint`, `npm run typecheck`, `npm run build`: as checagens. Para um arquivo só: `npx eslint <arquivo>`.
- **Não há suíte de testes nem test runner.** A verificação da lógica de servidor é um script contra PGlite (`@electric-sql/pglite`, já instalado como dev) usando as factories e queries que recebem `Database`, com as migrations reais aplicadas. Rode com `npx tsx` a partir de dentro do projeto (fora dele os pacotes não resolvem) e com o código dentro de uma `main()` assíncrona: os módulos do projeto rodam como CommonJS.
- Banco: `npm run db:generate` (gera SQL em `drizzle/` a partir de `src/db/schema`; revise o SQL), depois `npm run db:migrate`. `drizzle.config.ts` e `db:seed` leem o `.env.local`, ou seja, rodam contra o Neon configurado ali; não existe banco local separado.
- `npm run db:seed`: cria `admin@doubleone.com.br` com `SEED_ADMIN_PASSWORD`. É idempotente: nunca troca a senha, só garante o papel de admin.
- `npm run email:check -- voce@dominio`: testa o SMTP do `.env.local` (conexão e login) e manda os dois e-mails do Workboard (boas-vindas e nova senha) com dados de exemplo. Não toca no banco.
- `npm run cdn:check`: testa o CDN de arquivos de ponta a ponta (upload, recibo, listagem do `list.php`, CORS, proteções, exclusão) usando `MEDIA_CDN_URL`/`MEDIA_SIGNING_SECRET`. Não toca no banco. O PHP de `cdn/` não passa por lint nem typecheck, e não há PHP local.
- Tempo real (`realtime/`, Worker do Cloudflare com dependências próprias): `cd realtime && npm install`, depois `npm run dev` (porta 8787, segredo em `realtime/.dev.vars`), `npm run typecheck` e `npm run deploy`. Para o Next usar o Worker local: `REALTIME_URL=http://localhost:8787` e o mesmo `REALTIME_SECRET` no `.env.local`. Sem as duas variáveis, sino e chat se atualizam por recarga periódica. `npm run realtime:check` (na raiz) testa o Worker configurado no `.env.local` de ponta a ponta (conexão, entrega, proteções, desconexão e a sala dos quadros), como o `cdn:check`. Variáveis de ambiente do shell valem mais que as do `--env-file`: dá para apontar o check para o Worker local (`REALTIME_URL=http://localhost:8787 REALTIME_SECRET=... npm run realtime:check`).

## Arquitetura

**Fluxo de uma página autenticada.** `src/proxy.ts` (o antigo `middleware.ts` no Next 16) só confere se o cookie existe. Cada página é síncrona e põe, dentro de um `<Suspense>`, um componente que chama `requireSession()` ou `requireAdmin()` (`src/lib/session.ts`); veja `perfil/page.tsx` e `usuarios/page.tsx`. Para quem não é admin, `requireAdmin()` dá `notFound()`, sem redirecionar. Depois a página busca dados em `src/server/*` passando `db` e converte as linhas em tipos de view serializáveis (`types.ts`/`present.ts` ao lado da página, datas já formatadas por `src/lib/format.ts`) antes de entregar a client components. Route groups: `(auth)` é público, `(app)` tem o shell. A seção de admin da sidebar é renderizada em `(app)/layout.tsx`, dentro de `<Suspense>`.

**Mutações.** Server Actions em `actions.ts` ao lado da página retornam `ActionResult` (`{ ok: true, message }` | `{ ok: false, error, fieldErrors? }`), que os dialogs do cliente exibem via toast (sonner). O roteiro de cada ação em `usuarios/actions.ts`: `getAdminContext()` → `schema.safeParse` → carregar o alvo → travas sobre a própria conta → `auth.api.*` com `headers` → `recordAudit` → `refresh()` de `next/cache`. Os códigos de erro do Better Auth viram mensagens pt-BR em `API_ERROR_MESSAGES`.

**Montagem do auth.** `src/lib/auth-config.ts` exporta a factory `createAuth({ database, baseURL, secret })` com os hooks de auditoria (login, falha de login, logout, reset). `src/lib/auth.ts` liga a factory ao `db` do Neon e ao `env`. O Better Auth engole erros de `sendResetPassword`, então `captureResetDelivery()` usa `AsyncLocalStorage` para quem disparou o reset (o admin) saber se o e-mail falhou; sem esse store, o pedido veio do `/esqueci-a-senha` público, que registra `auth.password_reset_requested` e manda o e-mail depois de responder (`runInBackground`, ligado ao `after()` em `src/lib/auth.ts`).

**Uploads.** O arquivo vai do navegador direto para o `cdn/upload.php` na KingHost. O Next só assina: `/api/media/sign` gera um token HMAC que fixa caminho, tamanho exato, tipo e usuário; o PHP grava e devolve um recibo assinado; `/api/media/complete` confere o recibo (assinatura, dono, validade de 1 h), insere em `media` e audita. Repetir o recibo devolve o mesmo registro. O formato do token (`src/server/media/token.ts`) e a lista de extensões precisam bater com `cdn/lib.php`. `token.ts` e `keys.ts` não têm `server-only`, porque o `scripts/check-cdn.ts` os usa.

**Tempo real.** O Worker (`realtime/src/index.ts`) não tem banco: um Durable Object (`Hub`) guarda os websockets com o id da pessoa como tag. O Next grava no Neon e depois chama `POST /publish` (Bearer `REALTIME_SECRET`) dentro de `after()`; o navegador conecta com um token HMAC de 60 s pedido a `/api/realtime/token`. O formato do token e dos eventos é um arquivo só, `src/lib/realtime/protocol.ts` (só Web Crypto), que o Worker importa por caminho relativo; por isso o `tsconfig.json` e o ESLint da raiz excluem `realtime/`. No navegador, `realtime-store.ts` é um store fora do React (`useSyncExternalStore`) e `useRealtimeEvent` é o barramento; quem conta não lidas é sempre o servidor (`getInboxCounts`), o evento só avisa que mudou. Os quadros brancos usam o mesmo `Hub` com outra rota (`/board`): cada socket de sala leva as tags `<userId>` e `board:<id>` e os dados da sala no attachment (`serializeAttachment`), e o `/publish` pula esses sockets. O Worker não guarda o desenho: cada navegador grava os próprios elementos pela Server Action e a sala só repassa.

**Fronteira `server-only`.** O seed roda com `tsx`, fora do Next, e por isso não pode importar módulos com `server-only`. Código usado pelo seed ou pela config do auth importa `@/server/audit/recorder` (`createAuditRecorder(db)`), nunca `@/server/audit`. `src/env.ts` valida ao ser importado, então qualquer coisa que importe `@/db` exige as variáveis de ambiente.

**Dependências escondidas.** O "último login" em `listUsers` (`src/server/users.ts`) sai da `audit_log` (maior `createdAt` da ação `auth.sign_in`), então renomear ou deixar de registrar essa ação quebra a tela de usuários. As não lidas e as menções da lista de trabalhos (`listJobs`) e a linha de "novas mensagens" da página saem de `job_read.lastReadAt`, atualizado por `markJobRead` (ao abrir a página) e por `sendMessage` (quem responde já leu o que veio antes); um fluxo novo que mostre a conversa precisa marcar a leitura também. A ordem da Minha planilha mora em `job_assignee.position`: qualquer código que apague e recrie vínculos de funcionários (em vez de remover só quem saiu) joga o trabalho para o topo da planilha de todo mundo. O script de preferências no `<head>` (`src/lib/preferences.ts`) duplica a lógica de `applyTheme`/`applySidebar` em `src/components/preferences/preferences-store.ts`; os dois precisam mudar juntos. As notificações de mensagem somam numa linha só enquanto não lidas (índice único parcial `notification_open_job_message_idx`, usado como alvo do `onConflictDoUpdate` em `upsertJobMessageNotifications`): mudar o predicado do índice exige mudar o `targetWhere` junto. Quem recebe notificação de trabalho sai de `listMentionableIds` (funcionários ativos), a mesma lista das @menções. A página `/arquivos` decide o que está "sem uso" a partir de `listMediaLibrary` (`src/server/media/library.ts`), que conhece cada lugar que guarda arquivo (`user.image`, `client.logoKey`, anexos de trabalhos e do chat, imagens em `job.briefing` e `client.notes`, e o `fileId` das imagens nos elementos dos quadros): um campo novo de arquivo que não entre lá faz os arquivos dele aparecerem como sem uso e irem embora na limpeza. As conquistas de mensagens leem as tabelas de mensagens, reações, favoritas e anexos direto (`METRICS` em `src/server/achievements/core.ts`, a partir de `achievement_launch`): mudar como algo é gravado (ex.: o formato normalizado dos comandos, `normalizeMessageBody`) muda a conta. As fontes do Excalidraw ficam em `public/excalidraw/fonts` (cópia de `node_modules/@excalidraw/excalidraw/dist/prod/fonts`, sem a Xiaolai, que é chinesa e grande e cai no CDN deles): ao atualizar o pacote, copie de novo.
