## Projeto: Workboard

Sistema interno da agência (Double One) para controle de trabalhos. UI e mensagens em pt-BR.

- **Auth:** Better Auth com plugin `admin`, sem cadastro público. O "Esqueceu a senha?" do login é público (`/esqueci-a-senha` chama `/request-password-reset`, limitado pelo Better Auth a 3 pedidos por minuto): a resposta é sempre a mesma, conta desativada não recebe nada, e o e-mail sai em `after()` (`runInBackground` de `createAuth`), para o tempo de resposta não entregar quais e-mails têm conta. "Lembrar de mim" no login (ligado por padrão) é o `rememberMe` do Better Auth: ligado, sessão de 7 dias renovada com o uso; desligado, o cookie acaba ao fechar o navegador e a sessão dura no máximo 1 dia. Ligado, o e-mail fica no `localStorage` (`wb:login-email`) para vir preenchido, e a senha é oferecida ao gerenciador de senhas do navegador (`PasswordCredential`); a senha nunca vai para o `localStorage`. Config em `src/lib/auth.ts` (sem `server-only`, pois o seed importa). Em Server Components/Actions use `getSession`/`requireSession` de `src/lib/session.ts`; sempre revalide a sessão perto do dado, o `src/proxy.ts` é só otimista.
- **Cache Components ativo:** quem lê sessão/headers/cookies/searchParams fica dentro de `<Suspense>`; hooks de rota (`usePathname`, `useParams`) em componentes do shell também, na menor folha possível, porque em rotas com parâmetro (`/clientes/[slug]`) o caminho só existe no request e o build falha; nunca faça `await` de sessão no topo de layouts **nem de pages**. O `loading.tsx` não cobre a navegação entre páginas irmãs, e a validação de navegação instantânea do Next acusa o erro no overlay. Padrão: a page é síncrona e renderiza `<Suspense fallback={...}><Conteudo /></Suspense>`, e `Conteudo` chama `requireSession()`/`requireAdmin()`. Em página de admin, o título fica dentro do `Suspense` (fallback `PageSkeleton`), para não aparecer antes do `notFound()`. **Páginas guardadas:** com Cache Components o Next não desmonta a página ao sair, guarda escondida (`<Activity>`, até 3 rotas) com todo o estado; ao voltar ela reaparece como estava. Formulário de página (novo, editar, perfil, telas públicas) vai dentro de `<ResetOnNavigation>` (`src/components/reset-on-navigation.tsx`, chave `bfcacheId`): começa limpo a cada navegação por link e só restaura o rascunho no voltar do navegador. Formulário em dialog recebe uma `key` nova a cada abertura (contador), nunca uma chave fixa como "create". Rascunhos de mensagem (chat e trabalhos) ficam guardados de propósito. Sair recarrega a página inteira (`window.location`), para nada da sessão anterior sobrar escondido.
- **Banco:** Drizzle + Neon HTTP (`src/db`). Ao mudar `src/db/schema`, rode `npm run db:generate` e versione a migration em `drizzle/`. As chaves das tabelas do Better Auth precisam continuar em camelCase iguais aos campos dele.
- **Validação:** Zod 4 (`z.email()`, `z.url()`, `z.flattenError`, `z.prettifyError`). Schemas compartilhados em `src/lib/validations/`. Variáveis de ambiente validadas em `src/env.ts`.
- **UI:** shadcn/ui (estilo `base-nova`, sobre Base UI, não Radix: composição via prop `render`, não `asChild`). Adicione componentes com `npx shadcn@latest add <nome>`. Fonte Inter via `next/font`. Os componentes de `src/components/ui/` foram personalizados: um componente novo do shadcn chega no visual padrão e precisa ser ajustado aos tokens abaixo; não sobrescreva um existente com `shadcn add`.
- **Visual:** dashboard minimalista. Neutros + uma cor de destaque (`--primary`), bordas finas, sem gradientes, blur, glow ou sombras pesadas. A única exceção é o fundo animado das telas públicas (`<PatternWaves>` do React Bits, WebGL via `ogl`, em `(auth)/auth-background.tsx`), preto e branco como a marca da Double One e independente da cor de destaque. Texto de navegação 13px, rótulos `text-xs text-muted-foreground`. Use tokens (`bg-background`, `text-muted-foreground`, `border`), nunca cores fixas.
  - **Camadas** (a mesma linguagem do painel do shell): `shadow-control` em inputs e botões, `shadow-raised` em cards e tabelas, `shadow-overlay` em menus, dialogs e painéis. Controles (inputs, selects, botões) com 40 px (`h-10`) e `rounded-md`, para alinharem lado a lado; cards/tabelas/menus `rounded-xl`, dialogs `rounded-2xl`. Ícone no início de botão não muda o padding (só com `data-icon`), senão quebra os botões dentro de `InputGroup`. Tabelas de página vão dentro de `<TableFrame>`. Campos de data usam `<DatePicker>` (`src/components/date-picker.tsx`): digitação dd/mm/aaaa ou calendário com mês/ano em selects; valor `AAAA-MM-DD` (texto parcial enquanto incompleto, que o `z.iso.date()` recusa). Nunca `<input type="date">`.
  - **Cor de destaque em tom suave:** `bg-primary-soft` + `text-primary-ink` (badge e botão `soft`, ícone de estado vazio). Texto colorido usa sempre os tokens `*-ink` (`primary-ink`, `success-ink`, `warning-ink`, `destructive-ink`), que garantem 4.5:1 em todos os temas; `text-primary`/`text-success` puros só em ícones. Status em badges: variantes `success`, `warning`, `destructive`.
- **Shell:** `src/components/shell/` (`AppShell`, sidebar, header). O sino de notificações (`<NotificationBell>`) e a conta (foto, perfil, sair) ficam no canto do header (`user-menu.tsx`), com a saudação por horário (`src/lib/greeting.ts`, fuso de Brasília, calculada no servidor). No aniversário (`user.birthday`), a saudação muda e sobem balões (`<BirthdayBalloons>`), uma vez por dia por navegador. Nas datas especiais (`getHoliday`/`getHolidayGreeting` em `src/lib/greeting.ts`: Halloween de 29 a 31/10, Natal de 20 a 26/12, Ano Novo de 30/12 a 02/01, com alguns dias a mais para quem não trabalha no feriado), a saudação é a do tema e sobe a animação dela (`<HolidayEffect>`, desenhos em `holiday-animations.ts`: morcegos e fantasmas, neve, fogos), também uma vez por dia; clicar na saudação repete. O aniversário vem antes. Para conferir fora da época, `GREETING_PREVIEW_DATE=AAAA-MM-DD` no `.env.local` (só no `npm run dev`) finge essa data na saudação; as preferências de interface (tema, cor de destaque) no rodapé da sidebar, em Configurações (`settings-menu.tsx`). Novos itens de menu vão em `nav-config.ts` (`badge` mostra um contador do tempo real ao lado). O item da página aberta fica na cor de destaque (fundo tingido com `--primary` sobre `--sidebar`, texto e ícone `primary-ink`). Tooltips com `<Hint>` (`src/components/hint.tsx`).
- **Preferências** (tema claro/escuro/sistema, cor de destaque, sidebar recolhida, som dos avisos, comemorar entregas concluídas): `localStorage`, aplicadas no `<html>` (`.dark`, `data-accent`, `data-sidebar`) por um script antes da pintura (`src/lib/preferences.ts`) e lidas no React via `usePreferences()`. As telas públicas (login, redefinir senha) têm cores fixas: `data-fixed-theme` no `<html>` força o escuro grafite (tokens de `.dark` e a variante `dark:`) e desliga a cor de destaque. Quem põe o atributo é o script do `<head>` (lista `FIXED_THEME_PATHS`) e o `<FixedTheme>` do layout `(auth)`; página nova em `(auth)` entra na lista. Estilos da sidebar recolhida usam a variante `sidebar-collapsed:`. Novas cores de destaque: adicione em `ACCENTS` e um bloco `[data-accent=...]` no `globals.css`, conferindo contraste ≥ 4.5:1 do texto do botão; se a cor pura não der 4.5:1 como texto sobre o fundo e sobre `--primary-soft`, defina `--primary-ink` no bloco (claro e escuro).
- **Ações de admin:** só por Server Actions (`src/app/(app)/usuarios/actions.ts`), que revalidam o admin, validam com Zod, chamam `auth.api.*` e auditam. Os endpoints HTTP `/admin/*` do Better Auth ficam desligados (`disabledPaths` em `src/lib/auth-config.ts`). Ações que invalidam credenciais (senha, desativar) encerram as sessões do alvo; sobre a própria conta, nunca derrubar a sessão atual nem permitir se desativar/rebaixar.
- **Ações destrutivas:** irreversíveis (excluir) usam `<HoldToConfirmButton>` (segurar para confirmar) dentro de um AlertDialog; reversíveis (desativar) usam confirmação simples. Excluir usuário mantém a auditoria: `actor_id` vira null e nome/e-mail ficam copiados no evento. Nos trabalhos, autoria (cadastro, troca de status, mensagens) vira `set null` com o nome copiado; atribuições e leituras saem junto (`cascade`). Em tabela nova que referencie usuários, decida no FK entre `set null` e bloquear a exclusão.
- **Auditoria:** tabela `audit_log` genérica (ator, ação, entidade, `metadata` jsonb). Registre com `recordAudit()` de `@/server/audit` depois da operação dar certo; ele nunca lança erro. Ações novas entram no catálogo `src/lib/audit.ts` (rótulo + categoria) e, se tiverem campos novos em `metadata.changes` (`{ campo: { from, to } }`), em `AUDIT_FIELD_LABELS`. Para histórico de um registro (ex.: um trabalho), use `entity: { type, id, label }` e `listAuditLogs(db, { entity })`. Nunca registre senhas, tokens ou links de reset. Eventos de login/logout/reset são registrados pelos hooks do Better Auth.
- **Arquivos (uploads):** storage em PHP na KingHost (`cdn/`, instalação em `cdn/README.md`), links públicos com trecho aleatório. No navegador use `uploadMedia()` de `src/lib/media-upload.ts`, que envia direto ao CDN (sign → `upload.php` → complete); nunca passe arquivo pela Vercel (limite de 4.5 MB). A tabela `media` guarda só a `key`: monte a URL com `getMediaUrl()`. Para excluir, chame `deleteMedia()` de `src/server/media` a partir de uma Server Action (confere dono ou admin, apaga no CDN, remove o registro e audita). Tipos aceitos ficam em `MEDIA_TYPES` (`src/lib/media.ts`) e em `media_extensions()` (`cdn/lib.php`): mude os dois. O PHP do CDN roda em PHP 5 (compatível com 5.4+): nada de `??`, `strict_types` ou tipos escalares/de retorno. Sem `MEDIA_CDN_URL`/`MEDIA_SIGNING_SECRET`, as rotas respondem 503. Admins veem tudo em `/arquivos`, com onde cada arquivo é usado e o selo "Sem uso" (nada aponta para ele há mais de 24 h; mais novo pode estar num rascunho), e podem excluir os sem uso. Com o `cdn/list.php` no servidor (`listCdnFiles`), a tela cruza o banco com o que está de fato em `uploads/`: "Sem registro" (está lá, o banco não conhece; sai por `deleteUnregisteredMedia`) e "Não está no servidor" (registro com link quebrado). Sem o `list.php`, mostra só os registrados e avisa. O uso sai de `listMediaLibrary` (`src/server/media/library.ts`): **todo lugar novo que guarde arquivo (coluna com a chave, anexo, imagem em texto rico) precisa entrar lá**, senão o arquivo aparece como sem uso e pode ser apagado na limpeza. Anexos do chat e imagens de quadros pessoais aparecem sem nome, prévia nem link (são privados).
- **Perfil:** `/perfil` (pela foto no header), com Server Actions em `src/app/(app)/perfil/actions.ts`; os endpoints HTTP `/update-user` e `/change-password` do Better Auth estão desligados. A foto é opcional e fica em `user.image` como **chave do CDN** (pasta `usuarios`), não como URL: converta com `resolveMediaUrl()` no servidor e mostre com `<UserAvatar>` (`src/components/user-avatar.tsx`), que cai para as iniciais. Trocar ou remover a foto, ou excluir o usuário, apaga o arquivo anterior do CDN. O aniversário é `user.birthday`, campo adicional do Better Auth (`additionalFields` em `auth-config.ts`, coluna `date`): data pura `AAAA-MM-DD`, sem fuso, formatada com `formatCalendarDate()`.
- **E-mail:** `sendEmail()` em `src/lib/email`, por SMTP com nodemailer (`SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`; teste com `npm run email:check -- voce@...`). Sem `SMTP_HOST`/`SMTP_FROM`, em dev o e-mail só é impresso no terminal e em produção o envio fica desligado (`emailDelivery()`: `smtp`, `console` ou null; `isEmailConfigured()`). O módulo lê `process.env` direto, não `@/env` (entra na config do auth, que roda em scripts fora do Next). Os modelos ficam em `src/lib/email/templates.ts`, com a identidade das telas públicas: fundo preto, painel grafite, logo branco e botão claro, em HTML de e-mail (tabelas e estilos inline, cores fixas) e sempre com versão em texto. O logo vai anexado como PNG e referenciado por `cid:` (`src/lib/email/logo.ts`, gerado do `public/logo-double.svg`; o Gmail não mostra SVG). Hoje são dois: **boas-vindas** (`welcomeEmail`, ao criar usuário com "Enviar o acesso por e-mail" ligado: e-mail, senha e link do login; se falhar, a conta fica criada e o admin é avisado) e **nova senha** (`passwordResetEmail`, pedido pelo admin em Usuários ou pela própria pessoa em `/esqueci-a-senha`). Nunca registre a senha na auditoria (`user.created` guarda só se as boas-vindas saíram).
- **Clientes:** `/clientes` (lista), `/clientes/novo`, `/clientes/[slug]` (página) e `/clientes/[slug]/editar`, com Server Actions em `src/app/(app)/clientes/actions.ts`. Só admins cadastram, editam, arquivam e mexem no cofre; a equipe consulta. Ninguém exclui cliente: quem sai é **arquivado** (`archivedAt`), some das listas e da equipe e pode ser reativado. O slug sai do nome (`generateClientSlug`) e não muda depois. O logo é opcional, fica no CDN (pasta `clientes`) como `logoKey`, é preparado no navegador por `prepareLogo()` (sem recorte, com transparência) e só sobe ao salvar; trocar ou remover apaga o anterior. **Datas:** a fundação (`client.foundedOn`, o aniversário da empresa, com os anos completados) e outras datas importantes (`client_date`: nome, dia e `yearly`; com `yearly` repete todo ano a partir do dia, como um aniversário; sem, só no dia), editadas na seção "Datas" do formulário do cliente (a lista é regravada inteira quando muda, com `db.batch`) e mostradas no card "Datas" da página dele (`client-dates-card.tsx`, da mais próxima para a mais distante). Os erros das linhas vêm por caminho (`fieldErrorsByPath`: `dates.0.label`). As regras de dia ficam em `src/lib/calendar.ts` (`occasionOccurrences`, `nextOccurrence`) e `foundingOccasion` em `src/lib/clients.ts`.
- **Trabalhos:** `/trabalhos` (lista geral, **só admin**), `/trabalhos/novo` (só admin), `/trabalhos/[pit]` (página com briefing, detalhes, histórico e mensagens) e `/trabalhos/[pit]/editar`; Server Actions em `src/app/(app)/trabalhos/actions.ts`, consultas em `src/server/jobs.ts`. Só admins cadastram e excluem (exclusão leva mensagens, anexos no CDN e histórico). Editar, trocar status, ativar/desativar, ver briefing/histórico e conversar: admins em qualquer trabalho; o resto da equipe **só nos trabalhos em que está entre os funcionários** (`canAccessJob` no servidor, `findAccessibleJob` nas actions, `canSeeJob` nas páginas); fora disso o trabalho dá 404 / "não encontrado". Quem não é admin não pode se tirar do trabalho ao editar. Toda action nova que receba um `jobId` passa por `findAccessibleJob`. O PIT é `generatedAlwaysAsIdentity` (começa em 1, nunca é reaproveitado) e é o endereço do trabalho. Filtros da lista vão na URL (`params.ts`: `busca`, `situacao`, `status`, `cliente`, `funcionario` (`eu` = quem vê), `porPagina`, `pagina`); "Em aberto" = ativo **e** status que não encerra. **Cancelados:** trabalho num status de cancelamento (`isCanceled`) fica só no recorte `situacao=cancelados` (nem em "Todos": `listJobs` filtra `isCanceled` em todo recorte), fora dos relatórios e do Início (`loadReportJobs`), do calendário (`listJobsDue`) e dos trabalhos que dá para vincular a um quadro, e não conta como concluído (`isDoneStatus`/`isJobCompletion` em `src/lib/jobs.ts`: sem comemoração nem conquistas); a busca global ainda acha, por último. Só admins cancelam ou tiram de cancelado (`blocksCancellation` nas actions, `selectableStatuses` nos seletores; quem não é admin vê o selo parado), e o `<StatusSelect>` pede confirmação ao cancelar. Trabalho novo não começa cancelado. Uma consulta nova de trabalhos que alimente lista, conta ou agenda precisa decidir sobre os cancelados. Cliente e status são FK `restrict`: arquivar o cliente não mexe nos trabalhos, e status em uso não pode ser excluído. Gravações em várias tabelas usam `db.batch([...])` com o id gerado no app (`randomUUID()`), porque o driver neon-http não tem transação interativa.
- **Minha planilha:** `/minha-planilha` (todos) mostra os trabalhos em que a pessoa está, reaproveitando a barra, a tabela e a paginação da lista geral (`path` e `jobListHref(params, path)` em `params.ts`). Admins ganham abas com a equipe ativa (`?pessoa=`; ausente = a própria); para os demais o parâmetro é ignorado. Não lidas e menções são sempre de quem vê. Admins ganham a seção "Agência" (números gerais, carga da equipe e parados), com os dados de `loadReportJobs`. Recarrega sozinho a cada notificação ou mensagem (`HomeRefresher`).

Um planejamento por cliente (`planning.clientId` único), contínuo: o mês (`planning_month`) nasce quando alguém mexe nele. **Toda a equipe vê e edita**; só admins excluem o planejamento inteiro. Status (`PLANNING_STATUSES`: em produção, aguardando aprovação, ajustes pedidos, aprovado, finalizado) no mês e em cada post, **independentes**; a aprovação do cliente acontece fora do sistema. Finalizar o mês comemora (ver Comemoração), e os planejamentos têm aba própria nos Relatórios. Post: data, rede, tipo (`POST_KINDS`: estático, carrossel e reels, os do JSON, mais Stories e Vídeo só no cadastro manual), headline, texto de apoio, copy (só a legenda), CTA, hashtags (lista com #, `parseHashtags`), slides (`{headline, supportText}`, carrossel e Stories) e cenas (`{text}`, Reels e Vídeo); `keepKindParts` descarta o que não vale para o tipo. "Copiar legenda" junta copy, CTA e hashtags (`composeCaption`). O prompt e o leitor andam juntos: mudou o formato aceito, mude os dois. `planning_month.document` só existe nos meses importados do Word antes do JSON (só leitura).
- **Quadros brancos:** `/quadros` (lista com miniaturas, busca e recortes) e `/quadros/[id]` (o quadro ocupa toda a área de conteúdo); Server Actions em `src/app/(app)/quadros/actions.ts`, consultas em `src/server/whiteboards.ts`, regras em `src/lib/whiteboards.ts`. Post-its são retângulos coloridos sem borda (`customData.sticky`) criados pela paleta do rodapé, já abrindo a escrita. Imagens coladas sobem ao CDN (pasta `quadros`, via `generateIdForFile`) e o elemento guarda a **chave** no `fileId`; quem abre baixa do CDN (precisa do CORS do `uploads/.htaccess`). Excluir o quadro não apaga as imagens (podem estar em outro quadro): sem uso, saem pela tela de arquivos. A miniatura da lista é gerada no navegador (`exportToBlob`, WebP) e guardada no banco (`whiteboard.preview`), servida por `/api/quadros/[id]/miniatura`. Tipos de elemento aceitos em `WHITEBOARD_ELEMENT_TYPES` (sem os de IA, que rodam HTML).
- **Calendário:** `/calendario` (todos), mês em grade com as entregas (`job.dueDate`), os aniversários da equipe ativa (`user.birthday`; 29/02 cai em 28/02 nos anos comuns) e as datas dos clientes ativos (fundação e `client_date`, por `listClientOccasions`; arquivado sai), que levam à página do cliente e aparecem para todos, como os aniversários, sem depender dos filtros. Consultas em `src/server/calendar.ts`, datas em `src/lib/calendar.ts` (dias puros "AAAA-MM-DD", semana começando no domingo, como o `<DatePicker>`). Filtros na URL: `mes` (AAAA-MM), `situacao=todos` (inclui concluídos e inativos, apagados) e, só para admins, `quem=meus`; quem não é admin vê só os trabalhos em que está. No celular vira uma agenda com os dias que têm algo.
- **Relatórios:** `/relatorios` (só admin), em abas: visão geral, por cliente (`cliente=` abre o detalhe), por funcionário, prazos, etapas e planejamentos; período na URL (`periodo=` atalho ou `de`/`ate`, até 3 anos). As definições (cancelados ficam fora de tudo, inclusive das mensagens por pessoa; concluído = status atual encerra sem cancelar, com a data em `statusChangedAt`; no prazo = concluído até o dia da entrega; tempo até concluir = da criação à conclusão) ficam em `src/lib/reports.ts`, e as contas são funções puras em `src/server/reports.ts` sobre `loadReportJobs` (testáveis com PGlite). Por funcionário usa o vínculo de hoje (`job_assignee` não tem histórico); etapas usam `job_status_history`. A aba de planejamentos conta por mês (os meses que o período toca) e só vê o estado de agora (status de mês e post não têm histórico): posts e aprovados contra a meta, ajustes, meses atrasados (o mês começou sem aprovação), por cliente e por responsável; contas em `src/server/planning-reports.ts` sobre `loadPlanningReport`. Cada tabela tem `<ExportCsvButton>` (`;` e marca UTF-8, para o Excel em pt-BR) e a página imprime limpa: o shell tem `print:` que esconde sidebar e header, e o relatório imprime no tema claro. Gráficos em HTML/CSS, sem biblioteca.
- **Comemoração:** concluir um trabalho (passar para um status que encerra sem cancelar, vindo de um que não o dava por concluído) ou finalizar o mês de um planejamento (status do mês passa para "Finalizado"; post a post não) solta confetes e um som de conquista só na tela de quem concluiu: `celebrate()` de `src/components/celebration.ts`, com `isCompletion()` (trabalhos) ou `isPlanningCompletion()` (`src/lib/planning.ts`), chamados depois da action dar certo: no seletor de status, no quadro kanban e no formulário de edição dos trabalhos, e no `PlanningStatusSelect` com `celebrateDone` (o do mês). Um lugar novo que troque status precisa chamar também (e, do lado do servidor, as conquistas: `trackCompletion` em `trabalhos/actions.ts`, `onPlanningMonthStatus` nos planejamentos). Desligável nas Configurações ("Comemorar entregas concluídas"); com `prefers-reduced-motion`, só o som.
- **Status de trabalhos:** `/status-de-trabalhos` (admin) cadastra nome, cor da letra e do fundo, ordem (arrastando pela alça, com os sensores de `sheet-dnd.ts`; `reorderJobStatuses` recebe a lista inteira e recusa se ela não bate com o banco), o padrão de trabalho novo e quais encerram o trabalho (`isFinal`: sai de "Em aberto" e não conta como atrasado) ou o cancelam (`isCanceled`, sempre com `isFinal`, garantido por check no banco; a migration `0012` cria o "Cancelado"). O padrão não pode encerrar, cancelar nem ser excluído. Mostre com `<JobStatusBadge>` (cores do cadastro, fora do tema). O histórico (`job_status_history`) copia nome e cores no momento da troca: renomear ou excluir um status não reescreve o passado.
- **Mensagens dos trabalhos:** `job_message` guarda menções no texto como `<@userId>` (`mentionToken`/`splitMentions` em `src/lib/jobs.ts`) e os ids em `mentions`; o compositor troca "@Nome" escolhido na lista pelo token ao enviar. Só dá para mencionar os **funcionários ativos daquele trabalho** (`listMentionableIds`): a lista do compositor vem só com eles, e `sendMessage` descarta de `mentions` quem não é. Anexos sobem na hora para o CDN (pasta `trabalhos`) e entram em `job_message_attachment`; tirar do rascunho chama `discardAttachment` (apaga do CDN). Links, anexos e o envio de arquivos do compositor são compartilhados com o chat (`src/components/messages/`). Não lidas = mensagens de outras pessoas depois de `job_read.lastReadAt` daquela pessoa; a página do trabalho marca como lida ao abrir (inclusive as notificações dele no sino), recarrega na hora quando chega notificação daquele trabalho e também a cada 15 s com a aba visível (admins fora do trabalho não recebem notificação). Mensagens não vão para a auditoria (só a exclusão).
- **Tempo real:** websocket num Worker do Cloudflare (`realtime/`, instalação em `realtime/README.md`), fora da Vercel. O banco é a fonte de tudo: a Server Action grava e só depois avisa, com `publishRealtimeAfter(userIds, evento)` de `src/server/realtime.ts` (roda em `after()`, nunca lança erro). Eventos e token de conexão ficam em `src/lib/realtime/protocol.ts`, importado também pelo Worker: mudou, publique o Worker de novo. No navegador, `<RealtimeConnection>` (no `AppShell`) pede o token em `/api/realtime/token`, conecta, reconecta e cuida dos avisos globais; telas escutam com `useRealtimeEvent` e leem estado (contadores, "digitando…") com `useRealtime` (`src/components/realtime/realtime-store.ts`). Sem `REALTIME_URL`/`REALTIME_SECRET`, tudo funciona com recarga periódica: telas novas que dependam de evento precisam de um plano B quando `status !== "open"`. Desativar, excluir, trocar a senha ou encerrar as sessões de alguém derruba as conexões, inclusive as salas de quadro (`disconnectRealtimeAfter`). Os quadros brancos têm uma conexão à parte, só com o quadro aberto (`/board`, token por quadro conferido em `getBoardTicket`): o Worker repassa elementos e cursores entre quem está no mesmo quadro, e `closeBoardRoomAfter` fecha a sala quando o acesso muda (quem ainda pode volta com um token novo). As abas mandam um `ping` logo ao abrir: sem nada vindo delas, o fechamento pedido pelo servidor pode não chegar. Notificação do sistema (Windows/macOS) só com o Workboard aberto: uma aba líder (Web Locks) mostra, e só quando nenhuma aba está na frente com foco (`system-notifications.ts`); a permissão é pedida no sino. O som é sempre o do Workboard (`notification-sound.ts`, Web Audio, sem arquivo): toca uma vez só com várias abas (trava `workboard:som`), respeita a preferência "Som dos avisos" das Configurações, e a notificação do sistema sai muda para não tocar duas vezes.
- **Notificações:** tabela `notification` (quem recebe, tipo, quem fez com o nome copiado, trabalho e `data` com PIT, nome, status e trecho copiados no momento). Tipos e textos em `src/lib/notifications.ts`; consultas em `src/server/notifications.ts`; criar e avisar em `src/server/notify.ts` (`notifyAssignments`, `notifyStatusChange`, `notifyJobMessage`, chamadas pelas actions de trabalhos depois de dar certo). Recebem só os funcionários **ativos** do trabalho, nunca quem fez a ação. Mensagens do mesmo trabalho somam numa notificação só (`count`) enquanto ela não é lida (índice único parcial); quem foi @mencionado recebe "mencionou você" no lugar. Abrir o trabalho marca as notificações dele como lidas. Tipo novo: some em `NOTIFICATION_TYPES`, `notificationText`/`notificationHref` e na `NotificationRow` do sino.
- **Chat:** `/chat` (lista) e `/chat/[id]` (conversa), só 1:1, com Server Actions em `src/app/(app)/chat/actions.ts` e consultas em `src/server/chat.ts`. Uma conversa por dupla (`chat_conversation.pairKey` = os dois ids em ordem, `openConversation`). **Só quem está na conversa lê** (nem admins): toda consulta passa antes por `findConversation`, e para os outros a conversa dá 404. Não lidas e "Visto" saem de `chat_member.lastReadAt`; enviar marca como lido para quem envia. "Digitando…" vai direto pelo websocket (o Worker repassa, sem banco). Anexos na pasta `chat` do CDN. Só quem escreveu apaga a mensagem; mensagens do chat não vão para a auditoria. Pessoa desativada ou excluída: a conversa fica só para leitura (dá para favoritar, não para reagir nem fixar). `/chat/favoritas` mostra, no lugar da conversa, as mensagens favoritas da pessoa (do chat e dos trabalhos).
- **Busca global:** o campo "Buscar no Workboard…" no header (ou Ctrl/⌘+K, de qualquer tela) abre uma janela (`src/components/search/global-search.tsx`) que busca, pela Server Action `searchEverything`, em `globalSearch` (`src/server/search.ts`): trabalhos (nome, cliente ou PIT, também concluídos e inativos, com o status), clientes, mensagens dos trabalhos e do chat, arquivos anexados, links e caminhos do drive que aparecem nas mensagens (o caminho é copiado ao escolher), os links cadastrados dos clientes, os acessos do cofre (só serviço e link, nunca a senha), quadros e planejamentos; as páginas do menu são filtradas no navegador. **Cada grupo segue o acesso da tela de origem**: trabalhos e o que está neles só de quem está no trabalho (ou admins), chat só das conversas da própria pessoa (nem admins), quadros por `whiteboardVisibleTo`, clientes arquivados só para admins; uma regra de acesso nova numa tela precisa entrar aqui também. Ignora maiúsculas e acentos (`translate` no SQL, `foldText` no JS) e cada palavra precisa aparecer, em qualquer ordem. Valores de texto passados ao `concat_ws` precisam de `::text` (senão o Postgres não sabe o tipo do parâmetro).
- **Reações, fixadas, favoritas e comandos** (mensagens dos trabalhos e do chat): regras em `src/lib/messages.ts`, consultas em `src/server/messages.ts` (com `kind` "job" ou "chat"; não confere acesso, quem chama já passou por `findAccessibleJob`/`findConversation`), peças da tela em `src/components/messages/` (`message-tools.tsx`, `message-effects.ts`, `linkified.tsx`). **Reações:** lista fixa (`MESSAGE_REACTIONS`), uma por pessoa e emoji (`job_message_reaction`/`chat_message_reaction`); a minha aparece na hora (`useOptimistic` + `toggleReactionView`). **Fixadas:** `pinnedAt`/`pinnedByName` na própria mensagem, até `PINNED_MESSAGES_MAX` por conversa, num painel no topo para todo mundo dela. **Favoritas:** de cada pessoa (`*_message_favorite`); a lista só traz as que ela ainda pode ler, e o link leva até a mensagem (`#mensagem-<id>`, `messageElementId`/`jumpToHashMessage`). Reações e fixadas não notificam: avisam quem está com a conversa aberta pelos eventos `chat.updated`/`job.messages`. **Comandos** (`MESSAGE_EFFECTS`: `/confetti`, `/flip`, `/coffee`, `/party` e o secreto `/matrix`, que fica fora da lista; digitar "/" no começo da mensagem abre a lista de `VISIBLE_MESSAGE_EFFECTS`, `useSlashCommands` em `slash-commands.tsx`): a mensagem que é só o comando fica guardada normalizada (`normalizeMessageBody`), vira uma linha ("Ana mandou um café", clicar repete) e toca o efeito na tela de quem está com a conversa aberta quando ela chega há menos de 1 min (`useLiveMessageEffects`); prévias e avisos usam `messageEffectText`. **Caminhos do drive:** `splitMessageText` reconhece caminhos de pasta do Windows (`G:\Drives compartilhados\...` e `\\servidor\...`) e `<Linkified>` mostra um bloco com o botão "Copiar". Como nomes de pasta têm espaço, o caminho vai até o fim da linha (ou até um caractere que o Windows não aceita em nomes, ou um link): texto escrito depois dele na mesma linha entra junto.
- **Conquistas:** `/conquistas` (todos; as próprias e as de cada colega, `?pessoa=`), com o catálogo em `src/lib/achievements.ts` (id = nome da imagem em `public/conquistas/`, raridade, categoria, meta com barra de progresso, `secret`, `manual`) e as regras em `src/server/achievements/`. **Tudo conta a partir do lançamento** (`achievement_launch`, gravado pela migration): o que já estava no banco antes não entra. Três jeitos de desbloquear: (1) **ações do servidor** chamam `achievementsAfter(rótulo, (database) => onX(database, ...))` (`src/server/achievements/index.ts`, roda em `after()`, nunca lança erro) depois de dar certo: concluir trabalho (`onJobCompleted`, para os funcionários ativos, uma vez por trabalho), mensagens enviadas/apagadas, reações, fixar, favoritar, responsáveis, status do mês e posts dos planejamentos, quadros, post-its novos, perfil e o sino; (2) **eventos do navegador** (tema, cores, atalho da busca, resultado aberto, seções visitadas, segredos) vão por `reportAchievement()` à rota `POST /api/conquistas` (rota, não Server Action, para não entrar na fila da navegação), que confere o que dá (acesso à mensagem, ao trabalho, ao quadro); (3) a **checagem do dia** (`checkInAchievements`: primeiro acesso, aniversário, Natal, Ano Novo, Carnaval, sexta-feira 13 e tempo de casa pela data de cadastro), uma vez por dia em cada aba. O que o banco já guarda é contado direto nas tabelas (mensagens, reações, favoritas, anexos, menções); o que não guarda vira `achievement_record` (uma vez cada: trabalho concluído com `onTime`, mês finalizado, cor, seção, resultado da busca, post-it) ou `achievement_counter` (Ctrl+K, visitas ao perfil). Desbloquear (`grantAchievements`) nunca repete e uma secreta nova traz a "Isso É um Easter Egg?". **Avisos:** `user_achievement.seenAt`; o `<AchievementTracker>` (no `AppShell`) pede os não vistos (`claimUnseenAchievements`, só a aba visível; a primeira que pedir marca como vistos) ao abrir, ao voltar para a aba, no evento `achievement.unlocked` do tempo real e, sem ele, de minuto em minuto; o aviso (`showAchievementToasts`) usa o som `unlock` (preferência "Som dos avisos") e lendária solta confetes. As secretas ficam "???" para quem ainda não desbloqueou (mesmo na página de um colega). **Segredos:** Konami no Início e 10 cliques no logo (`AchievementTracker`/sidebar), a porta escondida da página de "não encontrado" (`NotFoundView`, em `app/not-found.tsx` e `(app)/not-found.tsx`) que leva a `/bastidores` (fora do menu e da busca, com o livro de visitas `guestbook_entry`), as cores na ordem do arco-íris nas Configurações (liberam a cor secreta `SECRET_ACCENT`, `data-accent="rainbow"`, que gira o tom em degraus de 1 s) e o `/matrix`. A "Caçador de Bugs" (`manual`) é concedida por um admin na página da pessoa (`setManualAchievement`, auditada). Imagens: o `next.config.ts` lista `public/conquistas` no build (`ACHIEVEMENT_IMAGES`) e `achievementImage()` cai para o emoji sem a imagem (em dev, imagem nova só depois de reiniciar o `npm run dev`). O "Explorador" usa as seções do `NAV_SECTIONS` que a pessoa vê: item novo no menu entra na conta. "Aprovado de Primeira" depende de `planning_month.adjustmentsRequestedAt` (gravado por `setMonthStatus` ao ir para "Ajustes pedidos"). Conquista nova: catálogo + regra no servidor + teste com PGlite.
- **Cofre de senhas:** tabela `client_credential`, ligada ao cliente. Senha e observações são cifradas com AES-256-GCM (`src/server/vault.ts`, chave `VAULT_ENCRYPTION_KEY`), com o id do acesso como dado autenticado (o texto cifrado não vale em outro registro). Os segredos nunca vão para o navegador nem para a auditoria: a lista sai de `listCredentials()` sem eles, e só `revealCredential` (admin) decifra, registrando `client.credential_viewed`/`_copied`. Sem a chave, o cofre fica desligado; perder ou trocar a chave deixa as senhas salvas ilegíveis.
- **Texto rico:** edite com `<RichTextEditor>` (Tiptap, carregado só no navegador; implementação em `src/components/rich-text-editor-impl.tsx`): títulos, fonte, tamanho, negrito/itálico/sublinhado/riscado, cor e marca-texto (paleta ou personalizada), alinhamento, listas, citação, links e imagens. Imagens: arquivo (botão, colar ou arrastar) só com `onUploadImage` (função estável), que prepara com `prepareContentImage` e envia ao CDN na hora; ou pelo link/colar HTML, com qualquer `https` (fica hospedada na origem). Arquivos enviados não são apagados se saírem do texto. Ao colar de fora, a formatação externa cai; dentro do editor, mantém. Na Server Action, passe o HTML por `sanitizeRichText()` (`src/server/rich-text.ts`: só tags e estilos do editor, imagens só `https`) e exiba com `<RichTextContent>`. Nunca mostre HTML que não passou pelo sanitizador. Na auditoria, registre só `richTextExcerpt()`.
- **Testabilidade:** `createAuth({ database })` e as queries em `src/server/*` recebem o `Database` por parâmetro, então dá para rodar contra PGlite (`@electric-sql/pglite`, dev) em scripts de verificação: `drizzle(new PGlite(), { schema })` e `migrate(db, { migrationsFolder: "drizzle" })` aplicam as migrations reais.
- **Checagens:** `npm run lint`, `npm run typecheck`, `npm run build`. O Worker (`realtime/`) tem as próprias dependências e fica fora dessas checagens: `cd realtime && npm run typecheck`.
