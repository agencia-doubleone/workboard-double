## Projeto: Workboard

Sistema interno da agência (Double One) para controle de trabalhos. UI e mensagens em pt-BR.

- **Auth:** Better Auth com plugin `admin`, sem cadastro público. Config em `src/lib/auth.ts` (sem `server-only`, pois o seed importa). Em Server Components/Actions use `getSession`/`requireSession` de `src/lib/session.ts`; sempre revalide a sessão perto do dado, o `src/proxy.ts` é só otimista.
- **Cache Components ativo:** quem lê sessão/headers/cookies/searchParams fica dentro de `<Suspense>`; hooks de rota (`usePathname`, `useParams`) em componentes do shell também, na menor folha possível, porque em rotas com parâmetro (`/clientes/[slug]`) o caminho só existe no request e o build falha; nunca faça `await` de sessão no topo de layouts **nem de pages**. O `loading.tsx` não cobre a navegação entre páginas irmãs, e a validação de navegação instantânea do Next acusa o erro no overlay. Padrão: a page é síncrona e renderiza `<Suspense fallback={...}><Conteudo /></Suspense>`, e `Conteudo` chama `requireSession()`/`requireAdmin()`. Em página de admin, o título fica dentro do `Suspense` (fallback `PageSkeleton`), para não aparecer antes do `notFound()`.
- **Banco:** Drizzle + Neon HTTP (`src/db`). Ao mudar `src/db/schema`, rode `npm run db:generate` e versione a migration em `drizzle/`. As chaves das tabelas do Better Auth precisam continuar em camelCase iguais aos campos dele.
- **Validação:** Zod 4 (`z.email()`, `z.url()`, `z.flattenError`, `z.prettifyError`). Schemas compartilhados em `src/lib/validations/`. Variáveis de ambiente validadas em `src/env.ts`.
- **UI:** shadcn/ui (estilo `base-nova`, sobre Base UI, não Radix: composição via prop `render`, não `asChild`). Adicione componentes com `npx shadcn@latest add <nome>`. Fonte Inter via `next/font`. Os componentes de `src/components/ui/` foram personalizados: um componente novo do shadcn chega no visual padrão e precisa ser ajustado aos tokens abaixo; não sobrescreva um existente com `shadcn add`.
- **Visual:** dashboard minimalista. Neutros + uma cor de destaque (`--primary`), bordas finas, sem gradientes, blur, glow ou sombras pesadas. A única exceção é o fundo animado das telas públicas (`<PatternWaves>` do React Bits, WebGL via `ogl`, em `(auth)/auth-background.tsx`), preto e branco como a marca da Double One e independente da cor de destaque. Texto de navegação 13px, rótulos `text-xs text-muted-foreground`. Use tokens (`bg-background`, `text-muted-foreground`, `border`), nunca cores fixas.
  - **Camadas** (a mesma linguagem do painel do shell): `shadow-control` em inputs e botões, `shadow-raised` em cards e tabelas, `shadow-overlay` em menus, dialogs e painéis. Controles (inputs, selects, botões) com 40 px (`h-10`) e `rounded-md`, para alinharem lado a lado; cards/tabelas/menus `rounded-xl`, dialogs `rounded-2xl`. Ícone no início de botão não muda o padding (só com `data-icon`), senão quebra os botões dentro de `InputGroup`. Tabelas de página vão dentro de `<TableFrame>`. Campos de data usam `<DatePicker>` (`src/components/date-picker.tsx`): digitação dd/mm/aaaa ou calendário com mês/ano em selects; valor `AAAA-MM-DD` (texto parcial enquanto incompleto, que o `z.iso.date()` recusa). Nunca `<input type="date">`.
  - **Cor de destaque em tom suave:** `bg-primary-soft` + `text-primary-ink` (badge e botão `soft`, ícone de estado vazio). Texto colorido usa sempre os tokens `*-ink` (`primary-ink`, `success-ink`, `warning-ink`, `destructive-ink`), que garantem 4.5:1 em todos os temas; `text-primary`/`text-success` puros só em ícones. Status em badges: variantes `success`, `warning`, `destructive`.
- **Shell:** `src/components/shell/` (`AppShell`, sidebar, header). O sino de notificações (`<NotificationBell>`) e a conta (foto, perfil, sair) ficam no canto do header (`user-menu.tsx`), com a saudação por horário (`src/lib/greeting.ts`, fuso de Brasília, calculada no servidor). No aniversário (`user.birthday`), a saudação muda e sobem balões (`<BirthdayBalloons>`), uma vez por dia por navegador; as preferências de interface (tema, cor de destaque) no rodapé da sidebar, em Configurações (`settings-menu.tsx`). Novos itens de menu vão em `nav-config.ts` (`badge` mostra um contador do tempo real ao lado). O item da página aberta fica na cor de destaque (fundo tingido com `--primary` sobre `--sidebar`, texto e ícone `primary-ink`). Tooltips com `<Hint>` (`src/components/hint.tsx`).
- **Preferências** (tema claro/escuro/sistema, cor de destaque, sidebar recolhida, som dos avisos, comemorar entregas concluídas): `localStorage`, aplicadas no `<html>` (`.dark`, `data-accent`, `data-sidebar`) por um script antes da pintura (`src/lib/preferences.ts`) e lidas no React via `usePreferences()`. As telas públicas (login, redefinir senha) têm cores fixas: `data-fixed-theme` no `<html>` força o escuro grafite (tokens de `.dark` e a variante `dark:`) e desliga a cor de destaque. Quem põe o atributo é o script do `<head>` (lista `FIXED_THEME_PATHS`) e o `<FixedTheme>` do layout `(auth)`; página nova em `(auth)` entra na lista. Estilos da sidebar recolhida usam a variante `sidebar-collapsed:`. Novas cores de destaque: adicione em `ACCENTS` e um bloco `[data-accent=...]` no `globals.css`, conferindo contraste ≥ 4.5:1 do texto do botão; se a cor pura não der 4.5:1 como texto sobre o fundo e sobre `--primary-soft`, defina `--primary-ink` no bloco (claro e escuro).
- **Ações de admin:** só por Server Actions (`src/app/(app)/usuarios/actions.ts`), que revalidam o admin, validam com Zod, chamam `auth.api.*` e auditam. Os endpoints HTTP `/admin/*` do Better Auth ficam desligados (`disabledPaths` em `src/lib/auth-config.ts`). Ações que invalidam credenciais (senha, desativar) encerram as sessões do alvo; sobre a própria conta, nunca derrubar a sessão atual nem permitir se desativar/rebaixar.
- **Ações destrutivas:** irreversíveis (excluir) usam `<HoldToConfirmButton>` (segurar para confirmar) dentro de um AlertDialog; reversíveis (desativar) usam confirmação simples. Excluir usuário mantém a auditoria: `actor_id` vira null e nome/e-mail ficam copiados no evento. Nos trabalhos, autoria (cadastro, troca de status, mensagens) vira `set null` com o nome copiado; atribuições e leituras saem junto (`cascade`). Em tabela nova que referencie usuários, decida no FK entre `set null` e bloquear a exclusão.
- **Auditoria:** tabela `audit_log` genérica (ator, ação, entidade, `metadata` jsonb). Registre com `recordAudit()` de `@/server/audit` depois da operação dar certo; ele nunca lança erro. Ações novas entram no catálogo `src/lib/audit.ts` (rótulo + categoria) e, se tiverem campos novos em `metadata.changes` (`{ campo: { from, to } }`), em `AUDIT_FIELD_LABELS`. Para histórico de um registro (ex.: um trabalho), use `entity: { type, id, label }` e `listAuditLogs(db, { entity })`. Nunca registre senhas, tokens ou links de reset. Eventos de login/logout/reset são registrados pelos hooks do Better Auth.
- **Arquivos (uploads):** storage em PHP na KingHost (`cdn/`, instalação em `cdn/README.md`), links públicos com trecho aleatório. No navegador use `uploadMedia()` de `src/lib/media-upload.ts`, que envia direto ao CDN (sign → `upload.php` → complete); nunca passe arquivo pela Vercel (limite de 4.5 MB). A tabela `media` guarda só a `key`: monte a URL com `getMediaUrl()`. Para excluir, chame `deleteMedia()` de `src/server/media` a partir de uma Server Action (confere dono ou admin, apaga no CDN, remove o registro e audita). Tipos aceitos ficam em `MEDIA_TYPES` (`src/lib/media.ts`) e em `media_extensions()` (`cdn/lib.php`): mude os dois. O PHP do CDN roda em PHP 5 (compatível com 5.4+): nada de `??`, `strict_types` ou tipos escalares/de retorno. Sem `MEDIA_CDN_URL`/`MEDIA_SIGNING_SECRET`, as rotas respondem 503. Admins veem tudo em `/arquivos`, com onde cada arquivo é usado e o selo "Sem uso" (nada aponta para ele há mais de 24 h; mais novo pode estar num rascunho), e podem excluir os sem uso. Com o `cdn/list.php` no servidor (`listCdnFiles`), a tela cruza o banco com o que está de fato em `uploads/`: "Sem registro" (está lá, o banco não conhece; sai por `deleteUnregisteredMedia`) e "Não está no servidor" (registro com link quebrado). Sem o `list.php`, mostra só os registrados e avisa. O uso sai de `listMediaLibrary` (`src/server/media/library.ts`): **todo lugar novo que guarde arquivo (coluna com a chave, anexo, imagem em texto rico) precisa entrar lá**, senão o arquivo aparece como sem uso e pode ser apagado na limpeza. Anexos do chat e imagens de quadros pessoais aparecem sem nome, prévia nem link (são privados).
- **Perfil:** `/perfil` (pela foto no header), com Server Actions em `src/app/(app)/perfil/actions.ts`; os endpoints HTTP `/update-user` e `/change-password` do Better Auth estão desligados. A foto é opcional e fica em `user.image` como **chave do CDN** (pasta `usuarios`), não como URL: converta com `resolveMediaUrl()` no servidor e mostre com `<UserAvatar>` (`src/components/user-avatar.tsx`), que cai para as iniciais. Trocar ou remover a foto, ou excluir o usuário, apaga o arquivo anterior do CDN. O aniversário é `user.birthday`, campo adicional do Better Auth (`additionalFields` em `auth-config.ts`, coluna `date`): data pura `AAAA-MM-DD`, sem fuso, formatada com `formatCalendarDate()`.
- **E-mail:** `sendEmail()` em `src/lib/email`. Hoje imprime no terminal em dev e falha em produção; o SMTP (nodemailer) entra trocando só esse módulo e `isEmailConfigured()`.
- **Clientes:** `/clientes` (lista), `/clientes/novo`, `/clientes/[slug]` (página) e `/clientes/[slug]/editar`, com Server Actions em `src/app/(app)/clientes/actions.ts`. Só admins cadastram, editam, arquivam e mexem no cofre; a equipe consulta. Ninguém exclui cliente: quem sai é **arquivado** (`archivedAt`), some das listas e da equipe e pode ser reativado. O slug sai do nome (`generateClientSlug`) e não muda depois. O logo é opcional, fica no CDN (pasta `clientes`) como `logoKey`, é preparado no navegador por `prepareLogo()` (sem recorte, com transparência) e só sobe ao salvar; trocar ou remover apaga o anterior.
- **Trabalhos:** `/trabalhos` (lista geral, **só admin**), `/trabalhos/novo` (só admin), `/trabalhos/[pit]` (página com briefing, detalhes, histórico e mensagens) e `/trabalhos/[pit]/editar`; Server Actions em `src/app/(app)/trabalhos/actions.ts`, consultas em `src/server/jobs.ts`. Só admins cadastram e excluem (exclusão leva mensagens, anexos no CDN e histórico). Editar, trocar status, ativar/desativar, ver briefing/histórico e conversar: admins em qualquer trabalho; o resto da equipe **só nos trabalhos em que está entre os funcionários** (`canAccessJob` no servidor, `findAccessibleJob` nas actions, `canSeeJob` nas páginas); fora disso o trabalho dá 404 / "não encontrado". Quem não é admin não pode se tirar do trabalho ao editar. Toda action nova que receba um `jobId` passa por `findAccessibleJob`. O PIT é `generatedAlwaysAsIdentity` (começa em 1, nunca é reaproveitado) e é o endereço do trabalho. Filtros da lista vão na URL (`params.ts`: `busca`, `situacao`, `status`, `cliente`, `funcionario` (`eu` = quem vê), `porPagina`, `pagina`); "Em aberto" = ativo **e** status que não encerra. Cliente e status são FK `restrict`: arquivar o cliente não mexe nos trabalhos, e status em uso não pode ser excluído. Gravações em várias tabelas usam `db.batch([...])` com o id gerado no app (`randomUUID()`), porque o driver neon-http não tem transação interativa.
- **Minha planilha:** `/minha-planilha` (todos) mostra os trabalhos em que a pessoa está, reaproveitando a barra, a tabela e a paginação da lista geral (`path` e `jobListHref(params, path)` em `params.ts`). Admins ganham abas com a equipe ativa (`?pessoa=`; ausente = a própria); para os demais o parâmetro é ignorado. Não lidas e menções são sempre de quem vê. A ordem é de cada pessoa: `job_assignee.position` (menor = mais acima; vínculo novo recebe `-(segundos desde 1970)` e vai para o topo). Arrastar (dnd-kit, `sheet-dnd.ts`) chama `moveSheetJob` com os vizinhos onde o trabalho caiu; `positionBetween` acha o meio e, sem espaço, `renumberSheet` renumera. Por isso, ao editar funcionários, só sai quem saiu e só entra quem entrou (apagar e recriar o vínculo perderia a ordem). `?visao=quadro` mostra um kanban com uma coluna por status (`jobs-board.tsx`, até `SHEET_BOARD_LIMIT`): arrastar na coluna reordena, soltar em outra coluna troca o status (com histórico e auditoria, como `setJobStatus`).
- **Início:** `/` é o "Meu dia" (partes em `src/app/(app)/_home/`, pasta privada que não vira rota): saudação por horário (ou de aniversário), uma frase de resumo, números pessoais, os próximos 7 dias em tira, agenda de entregas (atrasados, hoje, próximos 7 dias), "Precisa de resposta" (mensagens não lidas e menções nos trabalhos da pessoa e conversas do chat), atividade recente (o que os outros fizeram nos trabalhos dela; `src/server/home.ts`) e aniversariantes da semana. Admins ganham a seção "Agência" (números gerais, carga da equipe e parados), com os dados de `loadReportJobs`. Recarrega sozinho a cada notificação ou mensagem (`HomeRefresher`).
- **Planejamentos:** `/planejamentos` (visão do mês: todos os clientes com o status do mês e os posts aprovados), `/planejamentos/novo`, `/planejamentos/[slug]` (slug do cliente, `?mes=AAAA-MM`) e `/planejamentos/[slug]/editar`; Server Actions em `src/app/(app)/planejamentos/actions.ts`, consultas em `src/server/planning.ts`, regras em `src/lib/planning.ts`. Um planejamento por cliente (`planning.clientId` único), contínuo: o mês (`planning_month`) nasce quando alguém mexe nele. **Toda a equipe vê e edita**; só admins excluem o planejamento inteiro. Status (`PLANNING_STATUSES`: em produção, aguardando aprovação, ajustes pedidos, aprovado, finalizado) no mês e em cada post, **independentes**; a aprovação do cliente acontece fora do sistema. Os responsáveis (`planning_member`) recebem `planning.assigned` ao serem incluídos (ao criar ou editar, `notifyPlanningMembers`) e `planning.month_status`/`planning.post_status` no sino (`notifyPlanningStatus`). Finalizar o mês comemora (ver Comemoração), e os planejamentos têm aba própria nos Relatórios. Post: data, rede, formato (texto livre; o ícone sai de `formatKind`), tema, headline, copy (a legenda, com CTA e hashtags) e `sections` (jsonb `{label, text}`, na ordem). "Colar do Word": `parsePlanningDocument` (`src/lib/planning-import.ts`, roda no navegador) separa os posts pelos cabeçalhos "01 — 02/09 | TEMA" (também "Post N" e "02/09 | Tema"), lê "Conceito editorial", ignora a tabela "Calendário" e transforma os rótulos (Headline, Copy, Formato; o resto vira seção); a prévia deixa escolher os posts e o texto original fica em `planning_month.document`. Um rótulo novo que deva virar campo entra em `labelKind`.
- **Quadros brancos:** `/quadros` (lista com miniaturas, busca e recortes) e `/quadros/[id]` (o quadro ocupa toda a área de conteúdo); Server Actions em `src/app/(app)/quadros/actions.ts`, consultas em `src/server/whiteboards.ts`, regras em `src/lib/whiteboards.ts`. O desenho é o **Excalidraw** (`@excalidraw/excalidraw`, MIT), carregado só no navegador (`dynamic` com `ssr: false`) e só nessa página, em pt-BR, no tema do Workboard (`.wb-board` no `globals.css` pinta a interface dele com `--primary` e a fonte do app). Acesso (`whiteboard.access`): **pessoal** (só o dono, nem admin), **pessoas escolhidas** (dono, `whiteboard_member`, funcionários do trabalho vinculado e admins) ou **toda a equipe**; a regra está em SQL (`visibleTo`, para listas) e em código (`canAccessWhiteboard`, para a página e as actions): mude as duas juntas. Gerenciam (nome, acesso, vínculo, exclusão) o dono e, nos coletivos, os admins. Vinculado a um trabalho (`jobId`, `set null` se o trabalho for excluído), aparece no card "Quadros" da página dele. Quem é incluído recebe `whiteboard.shared` no sino. Excluir um usuário apaga os quadros pessoais dele; os coletivos ficam sem dono. **Gravação:** um registro por elemento (`whiteboard_element`, com a versão do Excalidraw); `saveWhiteboardElements` só aceita versão maior (empate: menor `versionNonce`, como o `reconcileElements`), então gravações repetidas ou fora de ordem não desfazem nada. No navegador, `BoardSync` (`quadros/[id]/board-sync.ts`) grava o que mudou ~1 s depois (em lotes), repassa na hora pela sala ao vivo (`board-room.ts`, websocket `/board` do Worker) e junta o que chega com `reconcileElements`; sem sala, busca as mudanças no banco a cada 10 s e ao voltar para a aba, pelo cursor do servidor (`getElementChanges`). O quadro pessoal não entra na sala (só o dono o vê; economiza o Worker): duas abas dele se acertam por essa busca. Post-its são retângulos coloridos sem borda (`customData.sticky`) criados pela paleta do rodapé, já abrindo a escrita. Imagens coladas sobem ao CDN (pasta `quadros`, via `generateIdForFile`) e o elemento guarda a **chave** no `fileId`; quem abre baixa do CDN (precisa do CORS do `uploads/.htaccess`). Excluir o quadro não apaga as imagens (podem estar em outro quadro): sem uso, saem pela tela de arquivos. A miniatura da lista é gerada no navegador (`exportToBlob`, WebP) e guardada no banco (`whiteboard.preview`), servida por `/api/quadros/[id]/miniatura`. Tipos de elemento aceitos em `WHITEBOARD_ELEMENT_TYPES` (sem os de IA, que rodam HTML).
- **Calendário:** `/calendario` (todos), mês em grade com as entregas (`job.dueDate`) e os aniversários da equipe ativa (`user.birthday`; 29/02 cai em 28/02 nos anos comuns). Consultas em `src/server/calendar.ts`, datas em `src/lib/calendar.ts` (dias puros "AAAA-MM-DD", semana começando no domingo, como o `<DatePicker>`). Filtros na URL: `mes` (AAAA-MM), `situacao=todos` (inclui concluídos e inativos, apagados) e, só para admins, `quem=meus`; quem não é admin vê só os trabalhos em que está. No celular vira uma agenda com os dias que têm algo.
- **Relatórios:** `/relatorios` (só admin), em abas: visão geral, por cliente (`cliente=` abre o detalhe), por funcionário, prazos, etapas e planejamentos; período na URL (`periodo=` atalho ou `de`/`ate`, até 3 anos). As definições (concluído = status atual encerra, com a data em `statusChangedAt`; no prazo = concluído até o dia da entrega; tempo até concluir = da criação à conclusão) ficam em `src/lib/reports.ts`, e as contas são funções puras em `src/server/reports.ts` sobre `loadReportJobs` (testáveis com PGlite). Por funcionário usa o vínculo de hoje (`job_assignee` não tem histórico); etapas usam `job_status_history`. A aba de planejamentos conta por mês (os meses que o período toca) e só vê o estado de agora (status de mês e post não têm histórico): posts e aprovados contra a meta, ajustes, meses atrasados (o mês começou sem aprovação), por cliente e por responsável; contas em `src/server/planning-reports.ts` sobre `loadPlanningReport`. Cada tabela tem `<ExportCsvButton>` (`;` e marca UTF-8, para o Excel em pt-BR) e a página imprime limpa: o shell tem `print:` que esconde sidebar e header, e o relatório imprime no tema claro. Gráficos em HTML/CSS, sem biblioteca.
- **Comemoração:** concluir um trabalho (passar de um status que não encerra para um que encerra) ou finalizar o mês de um planejamento (status do mês passa para "Finalizado"; post a post não) solta confetes e um som de conquista só na tela de quem concluiu: `celebrate()` de `src/components/celebration.ts`, com `isCompletion()` (trabalhos) ou `isPlanningCompletion()` (`src/lib/planning.ts`), chamados depois da action dar certo: no seletor de status, no quadro kanban e no formulário de edição dos trabalhos, e no `PlanningStatusSelect` com `celebrateDone` (o do mês). Um lugar novo que troque status precisa chamar também. Desligável nas Configurações ("Comemorar entregas concluídas"); com `prefers-reduced-motion`, só o som.
- **Status de trabalhos:** `/status-de-trabalhos` (admin) cadastra nome, cor da letra e do fundo, ordem, o padrão de trabalho novo e quais encerram o trabalho (`isFinal`: sai de "Em aberto" e não conta como atrasado). O padrão não pode encerrar nem ser excluído. Mostre com `<JobStatusBadge>` (cores do cadastro, fora do tema). O histórico (`job_status_history`) copia nome e cores no momento da troca: renomear ou excluir um status não reescreve o passado.
- **Mensagens dos trabalhos:** `job_message` guarda menções no texto como `<@userId>` (`mentionToken`/`splitMentions` em `src/lib/jobs.ts`) e os ids em `mentions`; o compositor troca "@Nome" escolhido na lista pelo token ao enviar. Só dá para mencionar os **funcionários ativos daquele trabalho** (`listMentionableIds`): a lista do compositor vem só com eles, e `sendMessage` descarta de `mentions` quem não é. Anexos sobem na hora para o CDN (pasta `trabalhos`) e entram em `job_message_attachment`; tirar do rascunho chama `discardAttachment` (apaga do CDN). Links, anexos e o envio de arquivos do compositor são compartilhados com o chat (`src/components/messages/`). Não lidas = mensagens de outras pessoas depois de `job_read.lastReadAt` daquela pessoa; a página do trabalho marca como lida ao abrir (inclusive as notificações dele no sino), recarrega na hora quando chega notificação daquele trabalho e também a cada 15 s com a aba visível (admins fora do trabalho não recebem notificação). Mensagens não vão para a auditoria (só a exclusão).
- **Tempo real:** websocket num Worker do Cloudflare (`realtime/`, instalação em `realtime/README.md`), fora da Vercel. O banco é a fonte de tudo: a Server Action grava e só depois avisa, com `publishRealtimeAfter(userIds, evento)` de `src/server/realtime.ts` (roda em `after()`, nunca lança erro). Eventos e token de conexão ficam em `src/lib/realtime/protocol.ts`, importado também pelo Worker: mudou, publique o Worker de novo. No navegador, `<RealtimeConnection>` (no `AppShell`) pede o token em `/api/realtime/token`, conecta, reconecta e cuida dos avisos globais; telas escutam com `useRealtimeEvent` e leem estado (contadores, "digitando…") com `useRealtime` (`src/components/realtime/realtime-store.ts`). Sem `REALTIME_URL`/`REALTIME_SECRET`, tudo funciona com recarga periódica: telas novas que dependam de evento precisam de um plano B quando `status !== "open"`. Desativar, excluir, trocar a senha ou encerrar as sessões de alguém derruba as conexões, inclusive as salas de quadro (`disconnectRealtimeAfter`). Os quadros brancos têm uma conexão à parte, só com o quadro aberto (`/board`, token por quadro conferido em `getBoardTicket`): o Worker repassa elementos e cursores entre quem está no mesmo quadro, e `closeBoardRoomAfter` fecha a sala quando o acesso muda (quem ainda pode volta com um token novo). As abas mandam um `ping` logo ao abrir: sem nada vindo delas, o fechamento pedido pelo servidor pode não chegar. Notificação do sistema (Windows/macOS) só com o Workboard aberto: uma aba líder (Web Locks) mostra, e só quando nenhuma aba está na frente com foco (`system-notifications.ts`); a permissão é pedida no sino. O som é sempre o do Workboard (`notification-sound.ts`, Web Audio, sem arquivo): toca uma vez só com várias abas (trava `workboard:som`), respeita a preferência "Som dos avisos" das Configurações, e a notificação do sistema sai muda para não tocar duas vezes.
- **Notificações:** tabela `notification` (quem recebe, tipo, quem fez com o nome copiado, trabalho e `data` com PIT, nome, status e trecho copiados no momento). Tipos e textos em `src/lib/notifications.ts`; consultas em `src/server/notifications.ts`; criar e avisar em `src/server/notify.ts` (`notifyAssignments`, `notifyStatusChange`, `notifyJobMessage`, chamadas pelas actions de trabalhos depois de dar certo). Recebem só os funcionários **ativos** do trabalho, nunca quem fez a ação. Mensagens do mesmo trabalho somam numa notificação só (`count`) enquanto ela não é lida (índice único parcial); quem foi @mencionado recebe "mencionou você" no lugar. Abrir o trabalho marca as notificações dele como lidas. Tipo novo: some em `NOTIFICATION_TYPES`, `notificationText`/`notificationHref` e na `NotificationRow` do sino.
- **Chat:** `/chat` (lista) e `/chat/[id]` (conversa), só 1:1, com Server Actions em `src/app/(app)/chat/actions.ts` e consultas em `src/server/chat.ts`. Uma conversa por dupla (`chat_conversation.pairKey` = os dois ids em ordem, `openConversation`). **Só quem está na conversa lê** (nem admins): toda consulta passa antes por `findConversation`, e para os outros a conversa dá 404. Não lidas e "Visto" saem de `chat_member.lastReadAt`; enviar marca como lido para quem envia. "Digitando…" vai direto pelo websocket (o Worker repassa, sem banco). Anexos na pasta `chat` do CDN. Só quem escreveu apaga a mensagem; mensagens do chat não vão para a auditoria. Pessoa desativada ou excluída: a conversa fica só para leitura.
- **Cofre de senhas:** tabela `client_credential`, ligada ao cliente. Senha e observações são cifradas com AES-256-GCM (`src/server/vault.ts`, chave `VAULT_ENCRYPTION_KEY`), com o id do acesso como dado autenticado (o texto cifrado não vale em outro registro). Os segredos nunca vão para o navegador nem para a auditoria: a lista sai de `listCredentials()` sem eles, e só `revealCredential` (admin) decifra, registrando `client.credential_viewed`/`_copied`. Sem a chave, o cofre fica desligado; perder ou trocar a chave deixa as senhas salvas ilegíveis.
- **Texto rico:** edite com `<RichTextEditor>` (Tiptap, carregado só no navegador; implementação em `src/components/rich-text-editor-impl.tsx`): títulos, fonte, tamanho, negrito/itálico/sublinhado/riscado, cor e marca-texto (paleta ou personalizada), alinhamento, listas, citação, links e imagens. Imagens: arquivo (botão, colar ou arrastar) só com `onUploadImage` (função estável), que prepara com `prepareContentImage` e envia ao CDN na hora; ou pelo link/colar HTML, com qualquer `https` (fica hospedada na origem). Arquivos enviados não são apagados se saírem do texto. Ao colar de fora, a formatação externa cai; dentro do editor, mantém. Na Server Action, passe o HTML por `sanitizeRichText()` (`src/server/rich-text.ts`: só tags e estilos do editor, imagens só `https`) e exiba com `<RichTextContent>`. Nunca mostre HTML que não passou pelo sanitizador. Na auditoria, registre só `richTextExcerpt()`.
- **Testabilidade:** `createAuth({ database })` e as queries em `src/server/*` recebem o `Database` por parâmetro, então dá para rodar contra PGlite (`@electric-sql/pglite`, dev) em scripts de verificação: `drizzle(new PGlite(), { schema })` e `migrate(db, { migrationsFolder: "drizzle" })` aplicam as migrations reais.
- **Checagens:** `npm run lint`, `npm run typecheck`, `npm run build`. O Worker (`realtime/`) tem as próprias dependências e fica fora dessas checagens: `cd realtime && npm run typecheck`.
